# 四、把仓库做成一个完整的整体

第三章记的是"做一件事并提交"。这一章记的是把散落的东西收拢成一个整体: 一个能跑起来的网站、一套能复现的流程、一份说得清的版本控制规矩。起因很朴素 —— 前置学习任务要交的是仓库链接, 而一个只有一份模板 README 的仓库交上去是不合格的。

这一章里所有数字都是本机实测的, 我会在每条后面标清楚是实测还是设计决定。

## 4.1 三个模块各归其位

收拢的过程中我先定了边界: 「凭据永远不进仓库, 其它该进的全进」。但真正动手拆的时候, 我发现这条边界不够用 —— 还得多问一句"这份东西给谁看"。

第一个模块是打卡工具, 第三章已经写完了。第二个模块是仓库原本定位的"算法题自动讲解" —— 之前它只是一句 README 描述, 现在它是一个真的能用的网页应用。第三个模块是学习笔记本身, 原来只有一个 DOCX, 现在 DOCX 与 Markdown 两份都在仓库里, Markdown 那份还带图片。

把它们串起来的是同一个东西: 「洛谷的登录态」。打卡要它, 自动取题面也要它 —— 这一点是实测出来的, 下面单独讲。

| 模块 | 入口 | 凭据需求 | 归属仓库 | 状态 |
| --- | --- | --- | --- | --- |
| 每日打卡 | luogu_punch.py | LUOGU_CLIENT_ID / LUOGU_UID | 公开仓库 luogu-explainer | 已完成, 自检 23/23, 单测 23/23 |
| 题目讲解站点 | web/ + explainer/ + server/ | MINIMAX_API_KEY 或用户自带 | 公开仓库 luogu-explainer | 已完成, 真实调用实测通过 |
| 学习笔记 | docs/notes/ | 无 | 私有仓库 luogubot | 已完成, DOCX 与 Markdown 双份 |
| 自研工具 | tools/ | 无 | 公开仓库 luogu-explainer | 已收录 17 个脚本 |

这张表里最重要的一列是"归属仓库"。它是这一轮最后才想明白的事 —— 我一开始是打算把东西全塞进一个仓库的, 拆开是后来被实测逼出来的, 原因记在第五章。

## 4.2 网页应用: 两种部署形态

题目讲解要调模型接口, 而模型密钥不能进浏览器 —— 前端是明文 JS, 放进去等于公开。所以架构上必须有一层服务端代理: 浏览器只跟本机服务说话, 密钥只留在服务端的进程环境里。这个决定是结构性的, 不是实现细节。

服务端我用标准库 http.server 写, 没上 FastAPI —— 因为本机没装, 而且这个服务只监听 127.0.0.1, 依赖越少越好。实测起来是这样:

```
$ curl -s http://127.0.0.1:8863/api/health
{"ok": true, "model": "MiniMax-M3.1-Flash", "base_host": "api.minimaxi.com",
 "has_key": true, "punch_ready": false, "version": "1.0.0"}
```

注意 has_key 只是一个布尔量 —— 接口只回答"密钥在不在", 绝不把密钥本身吐出去。这条我一开始就定死了: 任何响应体里不允许出现密钥。后来我把它写成了 CI 断言: tools/check_health.py 会检查响应里的字段名必须在白名单内, 任何一层嵌套都不许出现 api_key、secret、token、cookie 这些字段名, 也不许出现 LUOGU_CLIENT_ID 这类凭据字样。「把"响应里不许出现密钥"写成每次都跑的断言, 比写在文档里管用得多。」

真实调一次讲解, 用的就是这个服务:

```
$ curl -s -X POST http://127.0.0.1:8863/api/explain -H "Content-Type: application/json" --data-binary @req.json
{"ok": true, "usage": {"input_tokens": 369, "output_tokens": 2159}, "elapsed_ms": 14340}
```

14.3 秒, 输入 369 token, 输出 2159 token, 返回的是结构完整的 Markdown 讲解: 题目在考什么 / 思路推导 / 关键代码 / 复杂度 / 常见坑 / 自测题。

中间又踩了一个 Windows 的坑, 值得记: 我第一次用 curl 的 -d 传内联 JSON, 服务端返回"请求体不是合法 JSON"。查下来不是服务端的锅 —— 是 PowerShell 5.1 在把参数交给原生程序时把里面的双引号吃掉了。改成 --data-binary @文件 就好了。「这类问题一定要先怀疑自己那侧的 shell, 不要急着改服务端。」

但代理层这套形态有个前提: 得有一台一直开着的机器跑服务端。站点要放到 GitHub Pages 上给人看的时候, Pages 没有后端, 于是同一份前端必须能在"没有服务端"的情况下活下来。

我最后定的方案是三种形态, 页面启动时探测 /api/health, 探测不到就切形态:

| 形态 | 密钥在哪 | 能不能自动取题 | 适用场景 |
| --- | --- | --- | --- |
| 本机代理模式 | 服务端进程环境变量 | 能 (需洛谷登录态) | 本机开发与自托管 |
| 自带密钥模式 (BYOK) | 用户浏览器的 localStorage | 不能, 只能粘贴题面 | GitHub Pages 在线站 |
| 演示模式 | 不需要密钥 | 不需要 | 只想看效果的人 |

BYOK 这条路我先查了可行性才敢做: 带 Origin 头和 anthropic-dangerous-direct-browser-access: true 请求 MiniMax 的 Anthropic 兼容端点, 响应里确实带回了 Access-Control-Allow-Origin: https://gptsol56.github.io。「这不是我推测浏览器能用, 是我实测了响应头才敢把这条路写进前端。」

密钥只写进用户自己的浏览器 localStorage, 不经过任何服务器, 也不进版本库。演示模式那份样例是我真调用 MiniMax 生成的 (输入 514 token、输出 1150 token、耗时 14.54 秒), 但它是「预生成」的, 界面里我明确标了这一点 —— 预生成会过时, 不能让人以为看到的是实时结果。

## 4.3 取题接口要登录态, 于是和打卡共用了一套 Cookie

这一条是实测出来的, 而且推翻了我原本的假设。

我原以为洛谷的题目内容有公开 JSON 接口。实测: 匿名 GET /problem/P1001?_contentOnly=1 返回的是 SPA 的 HTML 空壳; POST /fe/api/problem/detail/P1001 返回 403, 错误类型明明白白写着 UserNotLoggedInException。也就是说「取题和打卡用的是同一套登录态 Cookie」。

这带来两个后果, 都是设计决定而不是补丁:

第一, explainer/ 的取题函数在拿不到题面时, 抛的错误必须写清"请设置 LUOGU_CLIENT_ID / LUOGU_UID, 或者直接粘贴题面", 而不是笼统地说"抓取失败"。UI 上也留了粘贴题面的入口 —— 没有登录态的人照样能用讲解功能, 只是要自己把题面贴进来。

第二, 密钥的存放方式被统一了: 打卡的两个变量、模型的三个变量, 全都走环境变量, Windows 上从注册表回退, 仓库里只留空的 .env.example。

这里我又撞了一次自己的记忆错误: 我之前在本轮开头说过"GitHub 通道不通, 得用 API 拼 commit", 结果重新做了一次纯 TCP 探测, github.com:443、ssh.github.com、api.github.com 全部通, gh auth setup-git 之后 git ls-remote 直接就能读私有仓库。「别把上一次的环境结论当成常驻事实」 —— 这是我这轮学到的第二条纪律, 第一条是"参考实现不等于接口真相"。

还有一条更硬的实测: 洛谷的接口响应里「没有 CORS 头」。这一条直接决定了打卡做不进网页 —— 浏览器会被跨域策略拦掉, 所以打卡只能在有服务端的地方做, 也就是命令行工具或者本机代理层。

## 4.4 版本控制: 这一轮我实际怎么做的

既然要交仓库, 提交记录本身就是要被打分的东西, 所以这一轮的提交我按团队标准来管, 而不是"改完一把 push"。

分支: 从 main 开功能分支, 改动都在分支上做, 合回 main 用 squash, 保持历史线性。私有仓库这一轮走的是 chore/notes-only-repo 分支。

提交: 一律 Conventional Commits, 而且一次提交只做一件事。这轮拆成了这样几笔 ——

| 仓库 | 提交 | 做了什么 | 为什么这么拆 |
| --- | --- | --- | --- |
| 公开 | feat(punch) | 打卡工具与它的配套 (测试/脚本/CI) | 工具本身和它的配套不该混在一笔, 将来要回滚工具时不必连测试一起撤 |
| 公开 | feat(web) | 讲解站点与代理层, 提示词抽成唯一真源 | 这是新功能, 单独一笔最好回滚 |
| 公开 | feat(site) | 站点构建脚本与 Pages 工作流 | 部署链路与业务代码分开, 部署出问题时回滚范围清楚 |
| 公开 | docs | 站点说明与工程规范 | 文档单独一笔 |
| 私有 | docs(notes) | 学习笔记与原始素材进库 | 笔记是这一阶段的记录本体, 单独成笔 |
| 私有 | chore(repo) | 项目代码迁出到公开仓库 | 迁出是一次显式动作, 要在历史里看得见 |

CI 门禁: push 与 PR 都会跑三个作业 —— test (Python 3.10 与 3.12 双版本, 加四套离线自检)、web-smoke (起服务、打 /api/health、断言响应里既没有 api_key 也没有洛谷凭据字段、再拉首页与两个静态资源)、static-site (组装静态产物并确认没有凭据字面量)。另外 Pages 部署单独一个工作流。

最后是那条老规矩: 推完必须回读。本地 HEAD 的 SHA 和远端 main 的 SHA 相同, 只是第一层; 远端 tree 的每个 blob SHA 与本地 git ls-tree 逐个对得上, 才说明服务端存的就是我本地这份内容。

## 4.5 两个仓库各装了什么

拆完之后两个仓库各管一摊, 边界是这样的:

| 仓库 | 可见性 | 装什么 |
| --- | --- | --- |
| gptsol56/luogu-explainer | 公开 | 讲解站点 (web/)、代理层 (server/)、讲解核心 (explainer/)、打卡 CLI (luogu_punch.py)、测试 (tests/)、CI 与 Pages 工作流 (.github/)、Dockerfile 与 docker-compose.yml、17 个自研脚本 (tools/), 共 48 个文件 |
| gptsol56/luogubot | 私有 | 四类笔记与提交日记 (docs/notes/, DOCX 与 Markdown 双份)、第一至第四天的原始素材与前置学习任务书 (docs/source-materials/)、DOCX 转 Markdown 的转换器 (tools/docx_to_md.py) |

被排除在外的只有三样: 凭据与密钥、虚拟环境与缓存、第三方源码树 (ECC 那三万多个文件)。最后一条我想了一下午要不要放 —— 放进去仓库会大一倍不止, 而且许可边界会变模糊, 所以不放, 改成在笔记里写清它是哪个项目、哪个版本、我用了它的哪一部分。

另外一样被排除的, 但原因不同: 「学习笔记本身」。它含姓名与学号, 所以只能在私有仓库里。

## 4.6 还没做的, 以及为什么

三件没做完的事, 写清楚比含糊过去好。

一, 「真实打卡还是没跑成」。洛谷登录态只在我浏览器里, 取出 __client_id / _uid 这一步没做。所以现在仓库里的状态是"工具已就绪、打卡待凭据"。等拿到凭据, 我要跑出一次真实的 code=200, 把那次输出补进第三章, 再打一个 tag。

二, 「题面自动抓取只覆盖了带登录态的情况」。没有 Cookie 的用户只能粘贴题面, 公开站点上更是只能粘贴题面 (洛谷没有 CORS 头)。这不是偷懒, 是接口本来就要登录 —— 但我承认, 一个"贴题面"的入口和一个"填题号"的入口摆在一起, 对不了解内情的用户还是有点怪, 这一点 UI 文案上还可以再打磨。

三, 「演示样例是预生成的」。它是我真的调了一次模型生成后存下来的, 但存下来之后模型再更新, 样例就会过时。我把它标注出来了, 但更彻底的做法是让演示模式也走实时调用, 只是那就需要密钥了。

> 这一章最想留下的一句话: "完整"不是把文件都堆进仓库, 而是「每个文件都知道自己为什么在那里、缺了会怎样」。凭据被排除在外不是因为它不重要, 而是因为它重要到不能进版本库; 第三方源码没放进来, 不是因为它没用, 而是因为放进来会改变这个仓库的性质。做这个决定的过程, 比我写的那点代码更值得记。
