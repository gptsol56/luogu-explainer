# 三、洛谷打卡助手：一次真实的 Git 提交

前面两章是理解：Git 是什么、Agent 是什么。这一章是落地 —— 我拿这两样东西真的做了一件事：给自己写了一个洛谷每日打卡的小工具，提交进自己的私有仓库，并把这次提交的过程原样记下来。《前置学习任务》里那句"有余力的同学可以尝试结合 AI Agent，对自己的项目使用 Git 进行版本管理"，说的就是我这一章干的事。

之所以挑"打卡"这件事：一是它足够小，一个晚上能写完；二是它的完成判据很硬 —— 服务端返回什么码就是什么码，不存在"差不多就行了"；三是它有真实网络调用，能把 Git 的完整流程（取证 → 写 → 提交 → 验证）真走一遍，而不是在本地敲几条命令自我感动。

## 3.1 这次提交是什么

起点是一个私有仓库 gptsol56/luogubot。提交之前它只有一次提交记录：9d30a82 "Initial commit"，三个文件 —— .gitignore（GitHub 的 VisualStudio 模板，7370 字节）、LICENSE、README.md（92 字节）。那个 README 里原本的一句话是 "an auto-explainer of the algorithm problems ,only for teaching and self studying"，而且 "problems" 和 "studyin g" 被人为断开成了两行。

这个仓库原本的定位是算法题自动讲解，不是打卡。我没有改它的定位，而是在里面加了一个独立模块：洛谷每日打卡助手。理由很简单 —— 这一阶段要交的是"仓库链接 + 提交记录"，那就让这个仓库里真的有我自己写、自己推上去的东西，而不是只有一份模板 README。

## 3.2 这个工具是怎么设计的

写之前我先定了三条原则，后来每一条都在踩坑时被验证是对的还是错的。

### ① 凭据只从环境变量读

洛谷的登录态靠 Cookie 里的 __client_id 和 _uid 维持。我参考的开源实现（kierankihn/auto-checkin）把它们写进 config.json —— 而那个文件是会跟着 git 一起进版本库的。我不想让自己的洛谷 Cookie 出现在任何一次 push 里，私有仓库也不行。所以我改成：环境变量 LUOGU_CLIENT_ID / LUOGU_UID，缺失时程序直接报错退出，并打印出获取步骤。仓库里只留一个 .env.example 这样的空模板，值是空的。

顺带一个 Windows 的细节：setx 写进去的变量只对新开的进程生效，当前终端读不到。这不是 bug，是 Windows 环境变量的机制，但第一次遇到时很容易以为自己代码写错了。

### ② 没有账号也能自证没坏

工具要在"我还没拿到凭据"的状态下也能证明自己是好的，否则就只能等真出问题才发现它坏了。所以我把逻辑判断拆成纯函数，给每个函数配了断言，再用 --selftest 串起来跑一遍，一行网络请求都不发。

```
$ python luogu_punch.py --selftest
洛谷打卡助手 离线自检
----------------------------------------------
  [PASS] cookie 拼接格式正确
  [PASS] code 201 且 message 含请登录 -> 判为凭据失效
  [PASS] punch_once 网络异常后重试成功
  [PASS] punch_once 非法 JSON 返回失败
  [PASS] _next_run 今天未到 / 已过
  [PASS] 时区回退链可用 (zoneinfo / pytz / 固定 UTC+8)
----------------------------------------------
自检结果: 23 passed / 0 failed
```

这 23 条断言覆盖了凭据的三类校验（缺失、格式错、正常）、六种返回码的解释、重试的次数与退避递增、非法 JSON、以及调度时间的计算。任何人 clone 下来先跑一次 --selftest，就知道工具的逻辑部分没坏 —— 不需要先有洛谷账号，也不需要联网。

### ③ 返回码不能靠猜

这一条是被实测打脸之后才补上的。洛谷的打卡接口是 GET https://www.luogu.com.cn/index/ajax_punch，靠 Cookie 认证，返回体形如 {"code":200,"message":"..."}。

我一开始是照着参考实现写的：code=200 是打卡成功，code=201 是今日已打卡。但我自己不带凭据打了一次真实请求，拿到的是 HTTP 200 + {"code":201,"message":"请登录洛谷进行打卡，获得今日运势。"} —— 也就是说，201 在没登录的时候也是 201。如果照抄参考实现，我的工具会在凭据完全无效的情况下报"今日已打卡"，而且退出码是 0。

改法是不把 201 硬编码成成功，而是 code 和 message 一起判：message 里带"请登录/未登录"就是凭据失效，其他情况才当已打卡。用一组占位凭据再打一次真实请求验证：

```
$ python luogu_punch.py --json --retries 1
{
  "ok": false,
  "code": 201,
  "message": "请登录洛谷进行打卡，获得今日运势。",
  "elapsed_ms": 1343,
  "attempts": 1,
  "http_status": 200
}
```

判成失败，退出码 1。真实凭据只存在我浏览器里 —— 仓库里没有，日志里没有，上面这段输出里也没有。这条占位凭据的请求不会产生任何打卡副作用，因为它根本没有有效的登录态。

| code | 参考实现的判断 | 我的判断（code + message） |
| --- | --- | --- |
| 200 | 打卡成功 | 打卡成功 |
| 201 | 今日已打卡 | message 含"请登录"→ 凭据失效；否则 → 今日已打卡 |
| 401 / 403 | 未处理 | 凭据失效，重新从浏览器复制 Cookie |
| 429 | 未处理 | 请求过于频繁，退避后重试 |
| 其它 | 未处理 | 未知返回码，报出具体数字 |

## 3.3 这轮踩的坑

按《前置学习任务》的要求，这里记的是真实遇到并解决的问题，不抄教程。

### ① 通道：github.com 连不上，绕了一圈又绕回来了

开始动手时 github.com:443 是连不上的，git clone 直接失败。我当时准备的方案是绕开 git 协议，改用 api.github.com 的 Git Data API 手工拼 commit：create blob → create tree → create commit → update ref。公开仓库我还找到了 ghfast.top 镜像能 clone 成功，但私有仓库不行 —— 镜像不转发 GitHub 凭据，报的是 "could not read Username for https://ghfast.top"（镜像在向我要用户名，它拿不到我的 GitHub 凭据）。

转折点是后来我做了一次纯 TCP 探测：github.com:443、ssh.github.com:443/22、api.github.com、ghfast.top 全部通。再执行 gh auth setup-git 让 git 走 gh 的凭证助手，git ls-remote 立刻就能读到私有仓库的 refs。于是标准 git 通道恢复了，我就老老实实用 git init / commit / push 提交，不再手工拼 API。

这件事我记下来是因为绕路那一步不是白费的：如果当时直接放弃 git 协议，我就不会知道"凭证助手"这一环；而最后决定用标准 git 而不是手工拼 commit，也正是因为绕路时看清了手工拼 commit 要做多少额外工作（blob 编码、tree 拼装、ref 更新、还要自己保证父子关系），那不是一个值得长期维护的做法。

### ② 201 有两种含义

就是 3.2 ③ 那件事。它的教训是具体的：参考实现不等于接口真相。同一个上游项目里，作者的判断可能只在"凭据有效"的前提下成立；而我的工具恰恰要在"凭据无效"的时候给出正确提示。所以读别人代码时，我把它当成"一个假设"，而不是"一个事实"，假设要自己验。

### ③ Windows 上的时区

定时打卡需要知道"北京时间现在几点"。Python 3.9+ 的 zoneinfo 看着最干净，但 Windows 上没有 IANA 时区数据库，ZoneInfo("Asia/Shanghai") 会直接抛 ZoneInfoNotFoundError，除非额外装 tzdata。

我的处理是三级回退：先试 zoneinfo，再试 pytz，最后退到固定的 UTC+8。最后这一档看起来像妥协，其实对当前是精确的 —— 中国自 1991 年起不再使用夏令时，Asia/Shanghai 就是恒定 UTC+8。所以这个回退不会算错，只会少一个依赖。同时我在 requirements.txt 里给 Windows 单独标了 tzdata，装依赖时就有它，不装也不会崩。

### ④ 中文提交信息

提交信息是中文的多行文本。我一开始想用 git commit -m "..." 内联，但命令行引号和编码的组合太容易出问题（这在前面那章讲过：命令行的引号会被 PowerShell 吃掉，报出来的错还完全误导）。最后改成把信息写进一个文件，再用 git commit -F 读文件提交。信息格式因此还能写成带空行的多段（第一行是标题，后面是原因），这在 GitHub 的提交列表里显示得更好。

### ⑤ 我自己脚本里的反引号

这个坑跟 Git 无关，但跟这一轮的干活方式有关。我用 Agent 生成 README 的内容时，README 里的 Markdown 代码块用的是反引号，而生成脚本是放在一段 JS 模板字符串里写的 —— 反引号把模板串提前截断，脚本直接语法报错。第一版 README 的代码块围栏被写成了 "`@bash" 这种半截样子。修法是先把内容里的反引号换成占位符，写完再统一替换回去。

记这一条是因为它符合一个规律：凡是"内容里要出现某种定界符"的场景，就一定会和生成它的代码里的定界符打架。写文档模板、写代码生成器、写正则，都要在脑子里过一遍这一条。

| 现象 | 根因 | 怎么解决的 |
| --- | --- | --- |
| github.com:443 连不上，私有仓库 clone 失败 | 本机到 GitHub 主站的网络被重置；镜像又不转发私有仓库凭据 | 先准备 API 拼 commit 的绕路方案；后测出通道恢复，改用 gh auth setup-git + 标准 git 提交 |
| 凭据无效时工具报"今日已打卡" | 照抄参考实现，把 201 一律当成功 | 改成 code + message 双重判定，用占位凭据实测到 HTTP 200 / 201 / 请登录 才落定 |
| ZoneInfo("Asia/Shanghai") 抛异常 | Windows 默认没有 IANA 时区数据库 | zoneinfo → pytz → 固定 UTC+8 三级回退，requirements 里给 Windows 补 tzdata |
| 中文提交信息可能乱码或被引号吃掉 | 命令行内联多行中文文本不可靠 | 提交信息写进文件，用 git commit -F 提交 |
| README 代码块围栏被截断 | 生成脚本用了 JS 模板字符串，内容里的反引号撞车 | 内容里先用占位符，写完统一替换 |

## 3.4 提交与验证

工作区的准备方式是先 init 再接上远端，而不是从零建仓：

```
$ git init -b main
$ git remote add origin https://github.com/gptsol56/luogubot.git
$ git fetch origin main
$ git reset --hard origin/main      # 让工作区带上原有的 LICENSE 与 .gitignore
$ git add -A
$ git commit -F _commit_msg.txt
$ git push origin main
```

那个 reset 是有意的：只有工作区里已经有 LICENSE 和原来的 .gitignore，我的改动才是"增删"而不是"重写"整个仓库 —— git diff 才是真的增量，提交历史也才读得懂。

push 的输出：

```
To https://github.com/gptsol56/luogubot.git
   9d30a82..74d7839  main -> main
```

但"push 显示成功"只是服务端收下了请求，不等于服务端存的就是我本地这份。所以我做了三层验证：

第一层，远端 commit SHA 与本地 HEAD 完全一致，都是 74d78394037b6db7887940b29b8a5474dc9c3986。

第二层，也是我认为最有价值的一层：把远端 tree 的 6 个 blob SHA 逐个拉下来，跟本地 git ls-tree 的结果对比，6 个全部一致。

```
$ git ls-tree -r HEAD
100644 blob 28134cf0ca406274d3bf5213beb7f1d6edf719a9  .env.example
100644 blob aa0f27ee996eca2a5054c33a311a346d2ecba1b9  .gitignore
100644 blob 30a8efb8d0ab19233adba35767ffbffff6211b55  LICENSE
100644 blob d475a55dffb18ac4386db93b55e1a61aad96a962  README.md
100644 blob ce8dd40ea6a60dedca337b8c4617828c547f680e  luogu_punch.py
100644 blob 5bf25fc2c26d5fe920407a8935ca1890a4e4bb6d  requirements.txt
```

第三层，用 gh api 把远端的文件列表和正文再读一遍，确认目录结构和我预期的一致、README 的中文没有乱码。

> 这件事让我改掉了一个习惯。以前我判断"提交成功了"的标准是命令没有报错；现在我要求看到内容级的证据 —— SHA 对得上才算数。Git 是内容寻址的，所以哈希一致就是最强的证据，这比看命令输出靠谱得多。

## 3.5 我的想法

这一章我最想留下的不是"我写了个打卡脚本"，而是三个想法。

第一个想法：这次提交里最花时间的部分，没有一件是"代码难写"。真正花时间的是环境和事实的核对 —— 网关通不通、镜像转不转发凭据、201 到底是什么意思、Windows 有没有时区库、生成的文本会不会被引号截断。这些问题没有一个能靠聪明解决，只能靠一次一次地去测。我以前对 Git 的理解偏向"记快照"这个功能层面，这次做完之后才真正体会到：它更重要的性质是内容寻址，是可以用哈希去证明"两端确实是一样东西"。

第二个想法：工具的质量不体现在它跑通的那一刻，而体现在它失败的那一刻。这次的 23 条断言、缺凭据时那段"请先设置 LUOGU_CLIENT_ID / LUOGU_UID，并告诉你去哪复制"的提示、返回码解释成中文人话 —— 这些都不是功能，是失败路径上的设计。写工具的时间分配大概是七成在正常路径，三成在失败路径，但这三成决定了别人愿不愿意用它。

第三个想法，也是我觉得最值钱的一条：把校验写进工具，而不是写进文档。我一开始想的是写一份 README 说明怎么用，后来发现不如让工具自己带一个 --selftest。这样做的好处是，任何人（包括三个月后的我自己）clone 下来跑一条命令就知道它没坏，而文档会被跳过、会被过期。既然是在讲 Agent，那这就是"可验证的外置大脑"的一个具体形态 —— 结论要自带证据。

还有一个没做完的事，得诚实记下来：这次没有真的打上卡。洛谷的登录态只存在我的浏览器里，把它取出来放进环境变量这一步我暂时没做。所以现在这个仓库里的东西是"工具已就绪、打卡待凭据"的状态 —— 代码路径全部跑通并自证过，但"今天真的打卡成功"这句话我没有证据，不能写。补上凭据、跑出一次真实的 code=200、把那次输出也补进这一章，是接下来要做的。

> 《前置学习任务》里说"笔记不要求篇幅很长，但是要沉淀自己的思想"。我这一章想留下的其实是同一句话的另一面：沉淀思想最快的方式，是把一次真实任务的完整过程写下来 —— 包括那些看起来很蠢、最后却决定成败的细节。写下来之后再回头看，才发现所谓"经验"，大多只是被认真记录过的错误。
