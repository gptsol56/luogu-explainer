# 五、拆仓库: 公开的站点与私有的笔记

第四章讲了怎么把东西收拢成一个整体。这一章反过来讲一件我一开始没做对的事: 收拢得过了头, 该拆的时候没拆。

## 5.1 为什么最后决定拆成两个仓库

我最初的方案是"除隐私信息外, 其余代码与信息都可上传" —— 也就是一个仓库全放, 靠 .gitignore 和提交前的检查挡住隐私。这个方案有三个具体的卡点, 全是实测撞出来的:

「卡点一: 私有仓库开不了 GitHub Pages。」 我对私有仓库调 POST /repos/gptsol56/luogubot/pages, 返回 HTTP 422, 响应内容是 "Your current plan does not support GitHub Pages for this repository." 当前套餐不支持私有仓库开 Pages, 而前置学习任务要交的是一个能打开的网站。站点不放进公开仓库就没有 URL, 这是死路。

「卡点二: 笔记里有不能公开的东西。」 学习笔记第一页就是姓名和学号。这不是"小心一点就好"的问题 —— 仓库一旦公开, 这些内容就是任何人点开链接就能看到的。靠提交前人工检查来保证, 迟早会漏。

「卡点三: 两种访问路径混在一个仓库里会互相拖累。」 打卡要洛谷登录态 Cookie, 而洛谷没有 CORS 头, 所以打卡必须在服务端做; 讲解反过来希望尽量没有服务端 (静态站 + 用户自带密钥)。这两种诉求放在同一个仓库, 最后的结果是站点被后端拖住, 打卡又被站点拖住。

想明白之后, 判断依据其实只有一条: 「这份东西给谁看」。代码和站点是给别人用的, 值得公开, 而且公开之后才有人用; 学习笔记是给自己的学习记录, 里面有个人信息, 留在私有仓库。

值得注意的是, 第三个卡点跟隐私无关, 跟版权无关, 纯粹是技术形态不兼容。「仓库该拆几个, 依据不是内容敏感度, 而是访问方式。」 我一开始想的是"按内容拆", 被这三个卡点教了一次。

## 5.2 拆完之后的结构

拆完之后是这样:

| 仓库 | 可见性 | 内容 | 访问方式 |
| --- | --- | --- | --- |
| gptsol56/luogu-explainer | 公开 | 讲解站点 + 打卡工具 + 全部代码 + CI + GitHub Pages | https://gptsol56.github.io/luogu-explainer/ 或 clone 后本机运行 |
| gptsol56/luogubot | 私有 | 学习笔记 + 原始素材 | 只有我自己能 clone |

历史不改写。私有仓库这一轮是用一次显式 commit (chore(repo): 项目代码迁出) 表达迁出的, 不 rebase、不 force-push。理由很实在: 提交记录本身就是要交的东西, 抹掉它等于把证据一起抹了。而且这次迁移本身就是一个值得记录的决策过程, 它在历史里应该看得见。

## 5.3 站点没有后端怎么还能用

Pages 没有后端这件事, 直接把"浏览器不能碰密钥"这条规矩变成了难题: 没有服务端替我保管密钥, 那密钥要么进浏览器, 要么功能就没了。

我选的是前者, 但加了两条约束。第一条: 密钥只写进用户自己的浏览器 localStorage, 不经过任何服务器, 也不进版本库 —— 想验证这一点可以直接看站点源码, 里面没有密钥, 只有用户自己填进去的那一个。第二条: 给不想填密钥的人留一条路, 就是演示模式, 提交一份预生成的样例讲解。

这里有个我做的时候才意识到的细节: 演示样例如果不做标注, 就是在骗人。读者看到一段完整的讲解, 会以为那是实时调用出来的。所以我在结果区的 meta 里明确写了"注意: 这是预先生成的样例, 不是实时调用"。「一个诚实的降级功能, 好过一个看起来很厉害的假功能。」

三种形态的切换逻辑很简单: 页面启动时 fetch /api/health, 成功就是本机代理模式, 失败就切 BYOK。这个探测本身也说明了问题 —— 静态站上这个请求会 404, 于是前端自然知道"没有后端"。

## 5.4 让提示词只有一份

改造过程中我发现一个很具体的技术债: 提示词原来写在 Python 代码里 (`build_prompt` 函数)。本机形态用服务端, 没问题; 但 BYOK 形态要在浏览器里拼提示词, 于是它就必须在 JS 里再写一份。两份一样的长字符串, 改一边忘了另一边, 本机看到的讲解和线上看到的讲解就会不一样 —— 而且这种不一致极难排查, 因为两边都能跑, 只是结果不一样。

解决办法是把提示词抽成独立文件 `explainer/prompt_template.json`: 后端 `load_prompt_template()` 读它, 前端 `fetch("prompt_template.json")` 读它, 同一个文件、同一份内容。模板里用 {{style}}、{{sections}}、{{problem}} 三个占位符, 两边各自做替换。

光有同一个文件还不够 —— 得防止有人改了一边。于是 explainer 的自检里加了两条断言: 一条检查 build_prompt 之后不残留未替换的占位符, 一条检查模板里的 required_sections 与代码里的 REQUIRED_SECTIONS 必须是同一份定义 (用元组相等来比)。自检从 22 条变成 25 条, 全部通过。

这件事让我意识到一个道理: 「重复不是问题, 没有机制阻止的重复才是问题。」 提示词写两份我改一次就行; 但只要没人保证两份一致, 我迟早会忘。把它变成一个每次都跑的断言, 才是真的解决。

删除之前我逐个确认了路径与大小, 删完再回读一次存在性 —— 写文件的脚本里每一步都有断言, 失败就立刻退出, 不会"删了一半还报告成功"。迁移的做法是「先复制、校验大小一致、再删源」, 这样即使中途断电也不会丢东西。

这批素材全部进了私有仓库的 docs/source-materials/。我特意给这个目录起名叫 source-materials 而不是 materials 或者 raw —— 因为它的含义是"这是输入不是成稿", 名字本身就是在提醒读的人别把它当成最终成果。

## 5.6 这一轮拿到的验证证据

按我在第三章立下的规矩, 结论要拿证据说话。这一轮的证据是这样拿到的:

| 验证项 | 方式 | 结果 |
| --- | --- | --- |
| 打卡工具自检 | python luogu_punch.py --selftest | 23 passed / 0 failed |
| 打卡工具单元测试 | python -m unittest discover -s tests | 23 条全部通过 |
| 讲解模块自检 | python explainer/luogu_explainer.py --selftest | 25 passed / 0 failed |
| 站点构建脚本自检 | python tools/build_site.py --selftest | 6 passed / 0 failed |
| 真实讲解调用 | POST /api/explain | ok true, 14.34 s, 输入 369 / 输出 2159 tokens |
| 浏览器直连模型 | 带 Origin + dangerous-direct-browser-access 请求 | HTTP 200, 带回 Access-Control-Allow-Origin, stop_reason=end_turn |
| 响应体无密钥 | CI 里 tools/check_health.py 断言字段白名单 | 通过, 且响应里不含任何凭据字样 |
| CI 与部署 | GitHub Actions 两个工作流 | CI 与 Deploy Pages 均 success |
| 站点可访问 | 拉线上首页与四个静态资源 | 全部 HTTP 200 |
| 远端与本地一致 | 远端 tree (recursive) 与本地 git ls-tree 逐个比 | 48 个文件 blob SHA 逐个一致, 0 差异 |

其中两条值得单独说。

一条是 blob SHA 的比对, 这里我又踩了一次坑: 我第一次调 GitHub 的 tree API 没带 recursive=1, 返回的只有 10 个 blob (顶层文件加一层目录), 而本地是 48 个。如果我就这么看下去, 会得出"远端少了 38 个文件"的结论, 然后开始瞎找原因。加上 recursive=1 之后才是完整的 48 个, 逐个 SHA 一致。「这跟第三章那次 201 的教训是同一类错误: 一个看起来像事实的数字, 其实是接口默认行为造成的假象。」

另一条是推送被拒。第一次用 gh repo create --push, GitHub 拒绝了, 提示 OAuth App 没有 workflow scope。查下来根因是环境变量 GH_TOKEN 覆盖了 keyring 里那个本来就有 workflow scope 的账号 —— 同一个机器上两个凭据, 优先级搞错了。清掉那个环境变量, 推送立刻成功。这件事让我意识到, OAuth scope 这种基础设施也是要学的: 它不在任何技术教程里, 但它会挡在你和"把东西交出去"之间。

## 5.7 我的想法

这一轮做完, 我想留下的不是"我建了两个仓库", 而是四件事。

第一件: 「拆仓库这件事本身比写代码难。」 写代码有明确的完成判据, 拆仓库没有 —— 你得判断哪些东西值得公开, 而这个判断会随着时间变化。我这次差点把"整理仓库"当成一件体力活, 结果真正的难点是在"给谁看"这个问题上。

第二件: 「实测和推断必须分开标注, 这一条救了我好几次。」 这轮有三处"我以为"被实测推翻: 以为洛谷有公开的题目 JSON 接口 (错, 要登录态)、以为 201 就是已打卡 (错, 也有未登录的含义)、以为私有仓库能开 Pages (错, 套餐不支持)。每一次如果我拿推断当结论去往下做, 后面都要返工。

第三件: 「降级功能也要诚实。」 演示模式是预生成的, 这一点必须写在界面上。预生成样例比空白页有用得多, 但如果不说清楚, 它就是在骗人。「一个标注清楚的降级方案, 好过一个看起来很厉害但会骗人的方案。」

第四件: 「哈希一致才是最强的证据。」 这轮最有价值的一次验收, 不是"命令没报错", 而是"远端 48 个 blob 的 SHA 与本地逐个相同"。反过来, 最有价值的一次踩坑, 也不是任何一条报错, 而是发现 tree API 默认只返回 10 个 blob —— 一个我差点当成事实的数字。Git 是内容寻址的, 所以只有哈希能证明"服务端存的就是我本地这份"。

> 第五章我最想留下的一句话: 「一个仓库该装什么, 取决于谁会读它。」 内容敏感度只是其中一个因素, 更硬的约束是访问方式 —— 谁能 clone、谁能访问 URL、需要不需要服务端。把这些想清楚, 仓库自然就分开了; 想不清楚, 就会像我一开始那样, 攒出一个谁都不好用的整体。
